# ADR-0006: Ranker → Critic 流水线中的轻量复核边界

**状态**：已接受  
**日期**：2026-07-27  
**决策人**：[姓名]

## 背景

在线诊断主链路中，Judge → Ranker → Critic 按流水线调度。为降低延迟，Ranker 每产出一个 Top-K 候选即可触发 Critic 的“轻量复核”。但如果不明确轻量复核的范围与最终结论的关系，可能导致：

- 流式决策过早输出不稳定结论；
- 轻量与全量复核标准不一致，引发逻辑冲突；
- Orchestrator 状态机复杂度过高。

## 决策

1. **轻量复核**：仅执行 Critic 反事实挑战清单的第 1 条——**移除候选根因，检查剩余告警是否可解释**。不执行链路双向一致性检查和多告警簇检查。
2. **全量复核**：等 Ranker 输出完整 Top-K 后，对最终候选执行完整 3 条反事实挑战。
3. **不允许提前放行**：轻量复核通过不等于最终通过，最终结论以全量复核为准。
4. **轻量复核的目的**：快速淘汰明显不合理的候选，减少 Ranker 后续重排或 Judge 补链的无效计算。

## 理由

- **第 1 条挑战计算成本低**：只需移除节点并检查剩余告警连通性/可解释性，无需额外图操作。
- **避免流式输出风险**：医疗/电信级运维场景要求最终结论稳定，不能因中途结果变化而抖动。
- **Orchestrator 状态机简化**：只需维护“流水线进行中”与“全量复核完成”两个状态。

## 后果

### 正面

- P99 延迟可优化：明显错误的候选被提前丢弃，减少后续处理。
- 最终输出质量不变：全量复核仍是硬门槛。
- 实现清晰：Critic 暴露两个内部接口 `light_review(candidate)` 与 `full_review(top_k)`。

### 负面

- 轻量复核被驳回的候选可能包含“真正根因但上下文不足”的误判，需全量复核时重新评估。
- 若 Ranker 产出候选速度较慢，流水线收益有限。
